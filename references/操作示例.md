# 可执行操作示例

首次使用状态 CLI、排查恢复或配置 worktree 集成时阅读。`{skill-root}` 是插件根，`{workspace-root}` 是用户项目根；所有状态命令使用同一主工作区根。

新项目先沿[初始化与交接](初始化与交接.md)建立早期检查点；本页其余示例适用于完整实施生命周期或专项恢复。

## 隔离演示

以下命令只创建自动清理的临时项目，真正执行应用验收和状态 CLI。审查 actor 是明确的合成角色，输出属于教程回归，不能作为用户项目的独立审查或宿主发布证据。

```text
python3 {skill-root}/scripts/demo_workflow.py --scenario planning
python3 {skill-root}/scripts/demo_workflow.py --scenario lifecycle
python3 {skill-root}/scripts/demo_workflow.py --scenario recovery
python3 {skill-root}/scripts/demo_workflow.py --scenario modify
python3 {skill-root}/scripts/demo_workflow.py --scenario worktree
```

演示源码 [`demo_workflow.py`](../scripts/demo_workflow.py) 是完整可运行示例，由前向测试持续执行。planning 路径验证实施前即有新鲜检查点且保留交接；另外四条路径验证应用输出、保留当前架构，并检查 `finish` 已清除检查点。

## 实际项目的最小路径

先确保 Git 忽略 `/.longtask/`，再初始化；后续变更始终读取返回的完整 `task_id` 和最新 `revision`，不要使用自拟标签代替它们。

```text
python3 {skill-root}/scripts/longtask_state.py init --root {workspace-root} --mode setup --goal "当前用户批准的目标" --actor integrator --output summary
python3 {skill-root}/scripts/longtask_state.py doctor --root {workspace-root}
python3 {skill-root}/scripts/longtask_state.py package --help
```

1. 为每个阶段实际产出证据，再使用 `evidence --kind phase:当前阶段` 和 `transition` 前进一步。例如离开 architecture 的证据种类是 `phase:architecture`。
2. 创建工作包合同，用工具返回的当前摘要作为 `base_revision`。进入 active 后才能写入声明写集；实际执行验收，再通过匹配 `acceptance_checks` 的 `--check-id` 记录包证据。
3. 完成包时复用原始输入合同并保留执行基线，按[工作包输入规则](状态协议.md#工作包-dag)构造 `--data`；不把带 evidence/运行时字段的工具输出对象直接回传。全部集成后重验必要检查，并记录 `kind=knowledge`，说明核对的当前文档。
4. 进入 review，由实际独立审查者提供绑定摘要和包范围的结构；批准者使用 `approve --scope review`，再记录 `phase:review`、转换 complete，并运行 `finish`。

完整字段和 JSON 的构造方式见可执行演示；权威要求见[状态协议](状态协议.md)，不要把示例中的模拟身份复制成真实批准。

## 验证失败后的同摘要恢复

产品审查发现与外部验证失败的边界见[状态协议·工作包 DAG](状态协议.md#工作包-dag)。恢复外部环境后，独立验证者重跑相同 `kind/check_id/summary`，在通过证据的 `details.recovery_observation` 中记录实际观察，然后进行新的独立审查和批准。只有这些步骤有效，才可在产品字节不变时重新完成。

```text
python3 {skill-root}/scripts/longtask_state.py evidence --root {workspace-root} --expected-task-id {id} --expected-revision {revision} --actor independent-tester --kind test --check-id service-health --summary "服务健康检查" --result pass --details '{"recovery_observation":"已恢复测试服务并重新观察到健康响应；具体版本和检查结果见验证输入"}' --output summary
```

该文本只能在确实获得所述观察后填写。失败 actor、工作包贡献者或批准者不能充当独立重验者；无关检查通过不能替代失败检查。`doctor` 会列出尚未满足的条件。

## 架构变更与 worktree

`modify` 在原任务冻结受影响包及消费者；批准新架构后，将旧包 supersede，以新 ID 建立合同。演示 `--scenario modify` 覆盖这一流程。

worktree 中只有集成者操作主工作区的 `.longtask/`，工作者只修改各自隔离目录。先声明不重叠写集与所有权；收集工作者的基线、实际 diff 和验收结果；集成到主工作区后重跑跨包检查。演示 `--scenario worktree` 实际创建隔离 worktree、交付文件并验证主根，不能替代真实多智能体并发评测。

## 故障恢复

遇到过期交接、租约或证据，先运行 `doctor`，处理诊断后重新冻结 `handoff`。选项中的 `available` 与 `unavailable_reason` 用于显示可用性；不要引导用户选择当前不可用的动作。

存储崩溃、部分日志和初始化/清理中断按[状态协议·故障恢复操作](状态协议.md#故障恢复操作)处理。恢复需要同版本备份和实际校验，不能通过手工调整完成字段消除错误。


## 预算定位与一次保存交接

包很多时先用有预算的 overview 查看诊断计数、阻断定位和目标线索，再按返回的 `pagination.next_offset` 逐页获取；比较各页 binding，变化时重新查询。索引仅供定位，`consumption.incomplete=true` 时不据此执行。

```text
python3 {skill-root}/scripts/longtask_state.py context --root {workspace-root} --view overview --max-chars 12000 --max-bytes 24000 --offset 0 --limit 10
python3 {skill-root}/scripts/longtask_state.py context --root {workspace-root} --view package --package-id {returned-package-id} --resume-choice resume
```

指定包查询仍保留全局风险和所有活动所有者，不代表帧已指向该包。详情中的输入引用需要实际读取；缺失或版本不符时协调，不能凭索引推断验收。极小预算拒绝输出要求增加预算；全部诊断可用 `doctor` 取数。精确预算和未加载合同见[状态协议](状态协议.md#有预算的-overview-与指定包详情)。

保存当前产物并立即交接时，构造经过当前目标/阶段/合同核对的新输入 JSON，一次调用：

```text
python3 {skill-root}/scripts/longtask_state.py checkpoint --root {workspace-root} --expected-task-id {current-task-id} --expected-revision {current-revision} --actor integrator --handoff-data '{new-handoff-input-json}' --output summary
```

`{new-handoff-input-json}` 是 `handoff --data` 的输入合同，不是工具输出的帧；具体字段见[结构化交接帧](状态协议.md#结构化交接帧)。不要同时传 `--next-action`。包需协调时此路径拒绝整个变更，先用普通 checkpoint/doctor 协调后读取最新双 CAS。保存有 `_runtime_warnings` 或恢复查询显示事件缺口时先协调日志，再交付该帧。
