# 新项目设计

本页供 `longtask-setup` 及修改相关设计的消费者按缺口读取，定义业务、技术、架构和界面设计的结果标准。文档归位、来源标签、命名与唯一权威由[文档架构](../文档架构.md#新项目输出合同)定义；本页不要求固定问卷、设计顺序或文件数量。规划充分性与出口见[初始化与交接](初始化与交接.md#规划充分性与出口)。

| 当前需要 | 读取范围 |
|---|---|
| 明确用户任务、本期范围和业务规则 | [业务问题与范围](#业务问题与范围) |
| 决定实现技术或解释取舍 | [技术推荐与决策](#技术推荐与决策) |
| 补足模块边界、状态、通信或运行设计 | [架构覆盖与核心链路](#架构覆盖与核心链路) |
| 为有界面项目形成视觉与交互合同 | [前端视觉与交互](#前端视觉与交互) |
| 判断答案是否已具体到可消费 | [设计消费示例](#设计消费示例)中的对应示例 |

## 业务问题与范围

业务内容用用户能判断的语言回答：谁在什么场景做什么，按什么规则，得到什么可观察结果。整理已有答案，仅保留会影响当前范围或关键合同的未决问题；不以全面提问替代方案，也不假定用户人数、规模、SLA、预算或行业要求。

| 内容 | 可消费的结果 |
|---|---|
| 目标与本期边界 | 当前用户任务、纳入/排除能力及来源；能解释核心场景为什么属于本期。 |
| 核心场景 | 角色、入口、前置条件、主要操作、成功结果和会改变设计的异常/权限分支。 |
| 业务规则 | 对象及其生命周期、谁可读取/修改/执行、合法状态变化、重复或冲突操作的结果；只写当前相关规则。 |
| 答案与来源 | 问题的当前答案及依据；区分用户明确事实、设计建议、推断和冲突，不把样例背景继承为事实。 |
| 影响与验收 | 答案影响的范围、页面/模块和可观察检查；未决项说明阻断什么、如何确认或验证。 |

可用问答表、场景描述或规则表表达，不要求把所有内容变成调查问卷。来源标注也适用于运行前提：设计者建议的输入、环境或操作约束保持推断/待确认，不能写成用户已经保证的事实。答案改变时沿业务关联更新相关合同与验收；不能只改技术设计而遗留相互冲突的业务答案。

## 技术推荐与决策

需要选型时给出适合当前项目的明确推荐，并解释它解决的实际问题和成本。候选只保留会改变实施或维护取舍的方案；不罗列产品目录，也不把本可分析的技术选择原样推给用户。

| 决策内容 | 应形成的结论 |
|---|---|
| 约束与职责 | 需求、团队经验、环境、数据/交互特征等已知依据；先确定要承担的职责，再引入组件。 |
| 推荐与理由 | 一个当前建议及对应收益；沿用用户明确的选择，存在真实冲突时定位影响。 |
| 实质备选与代价 | 可行备选、放弃原因，以及推荐增加的复杂度、运维、迁移或锁定成本。无实质备选时可说明原因。 |
| 状态与来源 | 使用[决策记录](../文档架构.md#决策记录)的状态；推荐保持 `proposed`，用户事实与授权来源另行引用。 |
| 核验与重评 | 对当前相关的版本、许可、维护状态及兼容性分别给依据，或明确未知、影响与核验方法；不能以一句“实施时验证”代替这些结论。说明什么条件会改变选择。 |

信息不足时可以给条件式推荐：明确默认建议成立的条件、哪项未知会改变结论，以及是否阻断当前实施。没有当前消费需求的缓存、队列、服务拆分或部署平台保留引入条件即可。

区分三种内容，避免把参数空缺误判为架构空缺，或用目标版本假装验证通过：

| 内容 | 例子与处理 |
|---|---|
| 架构决定 | 业务数据由哪个模块拥有、是否跨进程、采用何种存储；记录理由、状态与重评条件。 |
| 实施参数 | 端口、具体容量、超时、密钥引用和环境配置；放在消费它的工程/模块合同，缺失时说明适用范围及实施前的确认点。 |
| 未验证能力或证据 | 兼容性、性能、恢复可用性；在取得适用证据前标注未验证，给核验入口，设计陈述与原文摘要均不证明通过。 |

小型选择可留在现有章节；何时独立记录 ADR 仍按[决策记录](../文档架构.md#决策记录)，不为普通依赖制造决策文件。

## 架构覆盖与核心链路

架构用职责、状态归属、契约和失败行为表达。下表是检查当前相关区域是否足够深入的画布，不要求建立对应服务或分层目录；简单职责可以合并，不适用区域可以省略。

| 设计区域 | 应能回答的具体问题 |
|---|---|
| 业务与产品 | 谁执行用例；对象怎样变化；规则与权限由谁执行；结果如何验收。业务答案引用其唯一来源。 |
| 前端架构 | 页面与导航职责；本地、URL、服务器状态各由谁拥有；取数/提交、缓存失效、表单输入和结果反馈如何连接。无界面时省略。 |
| 通信与信任边界 | 实际跨模块/进程/外部边界在哪里；协议权威、输入输出、身份与授权、错误和兼容责任归谁。按需细化分页、数据表达或取消行为。 |
| 后端与业务处理 | 用例编排与业务规则分别归谁；事务覆盖哪里；外部失败如何返回或恢复。异步/重试场景再明确幂等、重复处理与一致性。 |
| 数据与集成 | 数据的唯一权威、读写者、生命周期与迁移责任；外部依赖是什么；跨存储/服务的一致性和故障边界在哪里。 |
| 运行与工程 | 构建/部署单元、配置与秘密的消费位置、测试入口、发布和必要恢复能力；观测怎样支持验收与诊断。只承诺当前所需能力。 |

区分职责层、业务模块、运行进程/部署单元和横切机制。模块内直接调用不必变成 RPC；契约和状态并不自动对应独立服务。系统图、职责表、状态表和接口合同应描述同一个系统，可以选择其中足以表达的形式。

影响设计的状态应能定位唯一权威、修改者、观察者与合法转换；缓存、前端副本、期望状态和实际状态需要区分，不能让多个模块各自声称拥有最终结果。跨边界合同应明确权威定义、生产者/消费者、验证责任和与当前场景有关的失败语义；不得用“统一接口”“完善异常处理”代替具体结果。

存在跨边界数据交换时，给出当前可消费的请求/响应或共享对象结构，逐项对齐消费者所需的字段、含义、状态判定依据与实际生产方及取数入口。生命周期变化或历史数据仍在本期范围时，这些数据也应可消费；不能把必需字段留给下游自行补约定。

对决定架构的核心场景，文档应能贯穿下列关系，允许通过已有合同引用表达：

> 用户入口与操作 → 业务规则/权限 → 接口或本地调用 → 处理模块 → 数据/状态变化 → 用户结果 → 验收

同时核对会改变该链路设计的失败：失败停在哪个边界、哪些状态已改变、用户怎样获知及恢复、重复尝试会产生什么结果。不必为每个场景复制完整系统图，也不为不存在的远程/异步操作增加超时或补偿机制。局部合同都完整而链路断开，仍是实际设计缺口。

## 前端视觉与交互

有用户界面时，设计文档应让前端消费者能实现并检查信息架构、核心交互和基础视觉。这些内容在前期形成；后期细节打磨沿[分段目标](任务推进.md#分段目标)推进。尊重用户提供的品牌、参考和技术选择；没有参考时，以真实内容、用户任务、使用频率、设备和信息密度解释建议，不以“现代、简洁、响应式”作为规格。

| 设计内容 | 可实施的结果 |
|---|---|
| 视觉依据 | 目标用户、主要任务、场景与内容密度；视觉方向、适用原因和继承参考的范围。 |
| 全局 Tokens | 语义色、字体/字号层级、间距、边框/圆角、焦点以及必要动效的具体值或可解析设计系统引用；区分建议值和已批准规范。 |
| 页面与信息架构 | 页面职责、导航关系、内容层级、主次操作和数据来源；页面围绕用户任务组织。 |
| 代表性布局 | 能展示主要信息密度及交互差异的页面规格与草图，注明区域内容、操作位置、组件和布局行为；可用 Markdown、线框或已有设计工具。 |
| 组件和状态 | 当前相关组件的默认、输入、禁用、加载、空、成功、错误和权限状态；说明触发、反馈和恢复路径，省略不适用状态。 |
| 适配与可访问性 | 窄屏重排、长文本/表格溢出、缩放；键盘操作及可见焦点、表单标签/错误定位、状态不只依靠颜色、必要的减少动效行为。结合实际页面说明。 |
| 验收 | 可检查的布局、交互、状态一致性和可访问性要求，关联相应用户场景；不能以实现者主观认为“美观”作为唯一通过条件。 |

全局规则保留唯一来源。相似页面复用，只写有实际原因的页面特例、覆盖哪些规则及为何覆盖；代表性页面应体现主要布局/交互类型，其他页面能据规则和差异继续实现，不强制逐页重复 Tokens。

只有会影响当前实现或选择时才细化规格。核心操作位置、信息层级、失败恢复等不能留成泛泛形容词；没有当前需求的主题切换、装饰动效或独立组件库不自动进入范围。草图说明布局意图，尚未运行的原型不构成应用验收证据。

## 设计消费示例

以下三个片段分别帮助产品、技术与前端消费者辨认所需深度。它们使用假设项目，不定义默认业务、技术栈、数值或批准来源；按实际需求选择表达形式，不复制为事实。

### 业务答案示例

| 问题 | 当前答案/来源 | 影响与检查 |
|---|---|---|
| 提交失败后是否保留输入？ | 建议保留本次表单输入供重试；`inferred`，尚待确认。 | 影响提交页与错误恢复；若接受，检查失败后内容不丢失，确认失败类型与重复提交规则。 |

该答案足以定位影响，但未获接受前不能写入批准验收。若涉及敏感输入的本地持久化，还需单独明确存储边界；“保留”不自动等于存入浏览器持久存储。

### 技术决策示例

| 决策 | 当前推荐与取舍 | 状态、核验与重评 |
|---|---|---|
| 列表筛选状态放在哪里？ | 在需要分享当前筛选结果的假设场景下，建议可表达的筛选条件进入 URL；临时输入留本地。纯本地备选更简单，但分享后无法复现。敏感条件不能放 URL。 | `proposed`；核验路由编码及返回导航行为。若筛选包含敏感条件或无分享需求，重新考虑。 |

这条结论可以放在前端合同，无需独立 ADR；它没有决定数据库或后端框架。

若选择包含运行时或依赖，核验摘要可以写为：“目标版本尚待核对，实施前查看目标环境及官方发行资料；许可未核验，按实际分发方式核对官方许可文本及义务；维护状态未核验，实施前核对官方支持周期与维护公告，若已停止支持则重评版本；兼容性未验证，在目标环境验证核心调用。”这是未知及解除方法的假设示例，不证明任何具体产品通过核验，也不要求普通状态归属选择套用依赖字段。

### 页面规格示例

假设“申请列表”场景需要查看状态、筛选和进入详情。页面引用全局 Tokens；其特例是高密度列表，正文使用较紧凑行距，操作与焦点区域仍可辨识。

```text
宽屏：标题 + 主操作
      筛选区
      结果数量 / 状态说明
      列表：申请标识、状态、更新时间、详情入口
窄屏：筛选可展开；每条结果保留标识、状态与详情入口，其余信息换行
```

加载保持筛选和标题稳定；无匹配结果给清除筛选入口；请求失败保留当前筛选并提供重试。状态以文字和视觉标记共同表达，键盘可进入筛选、主操作与详情入口。列表状态引用业务规则，不在页面文档重定义申请生命周期。验收可检查窄屏无关键操作遮挡、筛选后的结果反馈、失败后可重试和完整键盘路径。
