# 任务推进

需要选择主线/分支、分段交付或跨会话出口时加载相关章节。阶段、工作包和完成门仍由[状态协议](状态协议.md)定义；不另建目标或分支账本。

## 推进与停止条件

共享的目标延续、授权内推进与交付停止边界见[根技能](../SKILL.md#推进与停止条件)。本节只定义分支与保存的具体决策条件。

输入、依赖和授权明确时选择能缩小当前验收缺口的可交付切片；仅规划/审查的请求按对应产物选择动作。调查、重构和工具修复应服务当前验收或真实阻塞，明确出口及返回动作；可选建议不自动成为工作包或完成门。分支不再推进验收时，回到核心动作或用最小验证定位缺口，继续独立的已授权工作。

进入分支前明确其服务的验收、出口和返回动作；达到出口即返回主线，不因分支还有可选工作而延长它。

## 按需消费与验证

读取由当前决策驱动：先定位已有权威入口或索引，再读当前包的 `required_inputs`、受影响合同和相关章节；依赖或风险确实涉及其他模块时才展开。链接表示可导航的资料，不要求递归加载。只需规则/参数时不输出完整状态、schema 或脚本实现。

已读资料、校验输出和检查结论在来源版本、工作区、目标与适用范围仍一致且上下文可用时直接复用；补读遗漏的章节即可。资料改变、状态被其他写入者更新、范围/依赖变化、输出缺失或出现漂移诊断时刷新受影响输入；压缩后无法确认旧结论依据时重新查询。有效输出只用于决策，不代替写操作的双 CAS 和当前产物校验，具体绑定见[状态协议](状态协议.md)。

选择能覆盖变更及真实失败路径的检查；通过后继续下一项未满足验收。失败修复、受影响产物变化、证据过期或具体新风险触发重验；扩大范围需说明新增覆盖的故障模式。仓库要求的检查和最终集成完成门仍执行，不为同一未变版本反复跑全套，也不把旧摘要上的通过升级为当前通过。

## 发现与保存事件

在工作包出口、影响后续动作的重要决定、可复现失败/真实阻塞、依赖合同变化、可预见中断或交接时，保存能改变下一步的必要结论。一个事件只更新其所属权威记录；同一结论无变化时复用，不按每次工具调用、编辑或汇报追加保存。

结论至少说明受影响合同/验收、依据的固定版本或可复现定位、对下一动作的影响。失败后的已排除方案或验证限制若能避免恢复后重复尝试，保留有效条件和替代动作；未经验证的猜测不写成已观察事实，负面结果也不能超出实际检查范围。

临时执行结论通过状态 CLI 进入现有工作包、证据、blocker 或 `handoff`；难重建的调查事实、排除方案和失败条件可用 `discovery_checkpoint.py record/list/read` 保存与定向消费，唯一字段合同、非验证语义及版本/环境复核见[临时发现与恢复](状态协议.md#临时发现与恢复)。已声明的验收、阶段、测试或审查检查未满足执行前期望时，必须先保存实际 fail，不能看见失败后改称 discovery 来保留旧通过或跳过恢复。探索工具的非零退出不自动构成验收失败：原目标仅要求观察方案是否可用时，记录实际负面结果、适用条件和未验证项为非验证发现；若它违反已声明检查期望，仍按正式失败传播。不得事后改写检查合同。

同一次调查的相关事实、排除条件和明确标注的未验证假设，可以合为一份最小发现及一个显式新帧，不为每句结论建立独立事件。只需载荷或参数时，消费 CLI `--help` 与[发现输入合同](状态协议.md#发现输入合同)即可，不逆读实现寻找流程规则。

按实际中断位置保留能让恢复者继续的最小信息：

| 中断位置 | 保存边界与恢复动作 |
|---|---|
| 调查后 | 保存具体尝试、观察、排除条件、待确认结论及下一动作；恢复时定向 read，并核对适用版本、环境和重试条件。只读调查本身不制造验收 pass 或实施授权。 |
| 代码修改后 | 保存包状态和当前产物；有值得保留的发现时记录它，需要移交时显式提供已核对的新帧。包归属、租约或写集漂移先按现有诊断协调；没有运行的检查仍未验证，不能因保存成功宣称修改通过。 |
| 真实验证失败后 | 先记录实际检查的 fail，使包与消费者、批准和审查按状态协议失效；再补充可复用根因、已排除方案和重试条件。恢复时保留失败可见性，修复后运行适用重验与独立审查，discovery 记录不能解除失败。 |

helper 的可选交接由先保存发现、再保存新帧的两次 CAS 组成，不是原子交接；部分成功时准确报告已保存结论与未保存或不确定的帧，只用最新绑定重试明确的新帧。旧帧不自动重签，不把整段对话放进 reason；无需保存发现时直接使用 checkpoint 的组合保存，具体语义仍以[状态协议](状态协议.md#保存与定向消费)为准。

会影响项目长期行为、维护或验证的结论，按[知识合并与清理](../文档架构.md#知识合并与清理)更新现有架构/模块/决策来源；审查发现与修复复验按[审查协议](../专家审查协议.md#审查结论的去向)处理。可选建议不自动增加验收；不新增笔记、失败历史或审查日志，不在收尾丢弃仍影响项目的限制。

## 分段目标

将总目标拆成可独立验收的分段目标，默认按“骨架 → 血肉 → 皮毛”逐步填充。该顺序组织交付，不替代发现、架构、执行、审查等证据阶段：

| 层次 | 交付重点 | 进入下一段的依据 |
|---|---|---|
| 骨架 | 最小结构、必要接口和贯通的核心路径 | 代表性输入可走通核心链路；仅规划时则为可续接的边界与合同，不擅自实现 |
| 血肉 | 填齐已承诺功能、必要错误处理和实际集成 | 当前功能验收及必要可靠性检查通过，已知阻断保持可见并处理 |
| 皮毛 | 完善范围内的表达、易用性、展示与交付细节 | 剩余约定验收满足；可选美化不延迟完成 |

有界面项目的前期设计内容以[前端视觉与交互](新项目设计.md#前端视觉与交互)为准。信息架构、核心交互、基础视觉与可访问性参与前期合同，后段在该合同内打磨细节；不能因“皮毛”名称推迟这些基础设计或已承诺的界面验收。纯规划的深度与出口见[规划充分性与出口](初始化与交接.md#规划充分性与出口)。

每段用现有工作包的 `objective`、`dependencies` 与 `acceptance_checks` 表达成果、先后依赖和出口，不另建目标账本或新增状态字段。保持 `goal` 为总目标，不能每完成一段就改写它；`handoff` 指向当前段的具体包、必要输入及通过/失败后的下一动作。一个分段可以包含多个包，不要求机械建立三个包。

完成当前段后核对其版本绑定证据，再沿已授权依赖进入下一段；汇报已满足的验收与下一段缺口，不把单段通过当成总目标完成。已有项目、modify 或续接从实际缺口接入，复用已验证骨架；安全、正确性及当前阶段必需的验证前置，不以“后续完善”为由推迟。纯规划/审查、小范围修复和用户指定的顺序按实际范围适配，不扩成三轮建设。

## 会话预算与递进交接

优先在当前一个对话内完成已授权且规模可控的任务。先推进能形成验收结果的小步骤，按需加载、复用有效结论、缩短反馈，不为规划全部细节、重复历史或旁支讨论消耗上下文；不要为了使用 longtask 人为拉长任务或制造会话。

需要拆分时，除了按模块/领域纵向划分，也可按前后依赖横向划分步骤或时段。让每个片段具有在一个对话内完成的有界成果、验收和下一步；分段目标不必与会话一一对应，不以固定轮次或时间长度代替验收。职责独立且可并行时纵向拆分，强依赖链或同一写集连续完善时优先顺序递进，可按实际范围组合。

当前片段完成后，若剩余验收仍能在现有上下文可靠推进，则继续当前对话；输入规模、剩余步骤或上下文丢失风险已影响可靠性时，在清晰出口主动保存最小 `handoff`，供下一步骤续接。交接只带总目标、已验收成果的固定版本、当前段/包、剩余验收、必要输入和有效授权，不复制整段对话或重做上一步。仅片段完成时保留未完成检查点，不运行总任务 `finish`。

多窗口和顺序写入的交接边界见[拆分方向与递进移交](平行任务协作.md#拆分方向与递进移交)。创建、发消息和暂停会话仍遵循用户授权与宿主工具合同；没有相应能力时交付可复制的交接内容，不假称新会话已启动。自动压缩由宿主决定，技能只能减少触发压力并保留恢复兜底，不承诺禁止压缩。

## 变更与提交

只更新受影响的当前知识，遵循[文档架构](../文档架构.md#变更同步)。模块、依赖图、持久化或工作流变化使用 [modify](../skills/longtask-modify/SKILL.md)，按已有授权协调受影响闭包。

产生已授权的 Git 提交时，标题与正文默认中文，说明变更及目的；可保留仓库采用的 `feat:`、`fix:` 等前缀、代码符号和专有名词。用户或适用仓库约定指定其他语言时沿用；此偏好不增加提交、推送或合并授权。
