# Codex 当前版本发布与恢复

本文是 longtask 当前版本发布、安装和故障恢复的权威合同，仅供个人 Codex 宿主使用。目标版本见 `release-manifest.json.version`。

## 版本推进

本节是 longtask 维护者与发布者的版本判级、累计升级路径及同步范围的唯一规则来源。产品版本采用 `X.Y.Z`，依据[SemVer 2.0.0](https://semver.org/lang/zh-CN/)的合同影响分类；不以文件数、任务轮次或提交前缀判级。`release-manifest.json.version` 决定当前目标版本，其他版本字段是必须同步的消费者。

### 判级与升级路径

比较消费者可依赖的公开合同：技能入口和模式、用户指令与授权/完成边界、CLI 参数和输出、检查点结构/恢复政策、安装和宿主能力要求。以既有文档与批准合同为基准；代码偏离原合同的修复不自动构成破坏性变更，不能改写原意图来降低版本等级。

| 累计变化 | 版本动作 | 从 4.2.0 出发的示例 |
|---|---|---|
| 仅仓库过程、测试或 CI 维护；说明性文档润色，无执行合同变化，且不发布不同字节的新工件 | 保留当前版本，说明无发布需求 | 4.2.0 |
| 兼容修复、安全修复或内部调整，需交付新的修正工件；发布单纯说明性文档更新也归此级 | 补丁位加一 | 4.2.1 |
| 兼容新增能力、可选参数/宿主集成；公开能力弃用且旧用法仍支持 | 次版本位加一，补丁归零 | 4.3.0 |
| 删除/改变公开入口、必需参数、输出结构或合法输入语义，破坏授权/完成/恢复政策，或提高既有消费者无法满足的必需环境要求 | 主版本位加一，其余归零 | 5.0.0 |

同批变更取最高等级。技能 Markdown 中的执行规则也是产品行为合同，不能按普通文案处理；`docs:` 可包含破坏性改动，`feat:` 也不能证明兼容。确有未知合同影响时保留未知并继续有界调查；只有它影响选择且无法自行验证时才请求必要决定，不制造例行版本审批。

### 在开发中判定

开始维护或发现范围变化时读取当前清单、相关合同及可用的发布/标签信息，识别最近冻结的版本基线、该基线之后的累计差异和当前目标版本。已公开的候选预发布也算冻结；不能从“正式发布门未通过”推断它仍可修改。仅有本地标签/版本文件不足以证明远端已发布或未发布；信息不可得时明确未知，可先完成本地实现及版本建议，在外部发布前实际核验。

在设计范围确定时给出初步判级，在收尾/准备提交时按最终累计差异复核并执行已授权的本地版本同步，不能把这项检查推给用户，也不等发布脚本替模型判断。已有下一版本尚未公开时，后续兼容修复/功能合并到同一目标，不为每个提交或工作包再次递增；出现更高等级时从冻结基线重新计算。例如基线 4.2.0、目标 4.3.0 时再加兼容功能仍为 4.3.0，出现破坏性变更改为 5.0.0。

没有可用冻结基线时，用现有批准目标版本及已知差异作为暂定依据，报告其来源和不确定性，不能虚构发布记录。已有合法目标高于计算的最低路径时不自动降级或回退版本；保留既定目标并解释与最低路径的关系。用户明确版本策略优先，冲突时指出实际兼容影响，不能为凑指定版本把破坏性变更描述成兼容。

版本判断在本次交付说明或已有工作包/评测材料中保留：基线及冻结状态、累计变更与合同影响、判级、旧值 → 新值、兼容/检查点影响和已执行的同步/验证。不另建版本账本或任务档案。已授权的本地修改/验证包含相应版本同步；它不授权创建/移动远端标签、推送、发布或安装生产工件。

### 同步与验证

发生升级时，在同一变更中同步：

- `release-manifest.json.version`、`.codex-plugin/plugin.json.version`、根及 `skills/longtask/SKILL.md` 的 `metadata.version`；
- 状态运行时与源码校验器的 `SKILL_VERSION`、`references/state.schema.json` 的技能版本约束；
- 含精确版本的安装/构建示例、受影响合成 fixture/断言，以及实际行为或兼容性发生变化的说明；一般架构与模块说明引用当前版本合同，不重复版本号；
- `版本说明.md` 中唯一且非空的目标 `## X.Y.Z` 章节，写清累计能力变化、兼容性、升级动作和证据范围。

`schema_version` 只随状态格式合同变化独立判定，不随产品版本机械加一。次版本和补丁必须维持同一大版本的检查点恢复合同，不能仅因完整技能版本不同而拒绝；破坏已有结构、合法状态或恢复语义的变更必须推进大版本。兼容恢复保留原检查点版本和原证据绑定，具体要求见下文[兼容性策略](#兼容性策略)，不得手改版本号绕过校验。

先同步版本再构建新名候选，运行源码校验、适用的同大版本兼容、跨大版本拒绝、状态及打包测试与回归。源码校验机械检查合法目标版本、元数据/运行时/schema 一致性及唯一非空版本说明，不证明判级正确；判级正确性仍依赖合同比较和独立审查。凡实际工件改变，绑定旧工件的测试/宿主/恢复结果须按原证据合同处理，不能重签旧结果冒充新版本通过。

已公开版本的标签、资产和对应历史版本说明保持冻结；不同内容必须用新版本发布。当前 GitHub 候选合同使用裸 `X.Y.Z` 加 prerelease 标记，该标记不等同 SemVer 后缀，不添加未经安装/发布消费者支持的 `-rc` 或 `+build` 版本。没有改动冻结工件的同版重装、发布失败重试和解除 prerelease 标记不推进产品版本；更改已经公开候选的内容则另选新版本。

## 发布闭包

```bash
python3 scripts/build_release.py build --root . --output dist/longtask-4.6.2.zip
python3 scripts/build_release.py verify --root . --archive dist/longtask-4.6.2.zip
```

`release-manifest.json` 定义唯一发布闭包；其中排除 `evals/*_results.json` 及指定结果、trace、快照目录等易变执行产物（仓库归属见 [AGENTS.md](../AGENTS.md#源码与产物架构规范)）；随包保留案例、协议与测试。重新记录时间或耗时不会改变发布字节；修改任何随包指令、合同或代码仍会改变摘要并要求匹配的新证据。其中不得包含 `.claude`、`.claude-plugin`、历史归档、`.longtask/` 临时检查点或 `docs/tasks/` 旧任务记录。构建和验证都必须失败关闭，并限制文件数、单文件大小、总大小、链接和路径类型。任何子目录无法枚举都终止构建及源码验证；验证/提取会非阻塞打开归档并拒绝 FIFO 等非普通文件。

发布包内的 `release-manifest.json` 定义源码闭包，`release-integrity.json` 记录逐文件摘要、大小及模式；两者名称在忽略大小写的文件系统上也不同。构建和归档检查在任何提取写入前拒绝路径各分量经 Unicode NFC 与大小写折叠后的别名、文件/目录冲突及完整性清单名称占用。模式是跨平台发布元数据：`build_release.py`、`longtask_state.py`、`run_forward_evals.py`、`run_skill_evals.py`、`validate_longtask.py` 五个 `scripts/` 入口固定为 `0755`，其他文件为 `0644`；不从 Windows `st_mode` 推断可执行位。POSIX 提取显式设置模式，installed 自检另核对实际可执行位；Windows 由固定模式合同重建并核对工件，访问控制使用原生 ACL。

源码、归档及目的目录从卷根逐分量固定句柄，枚举、读取、创建、替换、清理及目录刷新均使用同一平台后端；不得先解析链接再普通路径打开。Windows 原生后端与文件系统边界见[原生文件系统能力](平台适配器.md#原生文件系统能力)。暂存发布保留具有重命名权限的同一源句柄，错误失败关闭；归档以二进制读取，使 CRLF、控制字符与 NUL 原样参与摘要。

脱离源码工作区验证或提取时，必须携带由受信渠道取得的非空 SHA-256：

```bash
python3 scripts/build_release.py verify \
  --archive dist/longtask-4.6.2.zip \
  --expected-sha256 '<trusted-sha256>'

python3 scripts/build_release.py extract \
  --archive dist/longtask-4.6.2.zip \
  --destination '<empty-staging-directory>' \
  --expected-sha256 '<trusted-sha256>'
```

## 个人 Codex 安装

安装前检查 `~/.codex/skills/longtask`；若存在旧的独立技能副本，先备份到技能发现目录之外，避免它与当前插件产生同名入口。此操作只清除发现冲突，不修改项目检查点，兼容范围按下文[兼容性策略](#兼容性策略)核对。

将校验并提取出的完整目录原子放到 `~/plugins/longtask`。默认个人市场位于 `~/.agents/plugins/marketplace.json`：文件不存在时可直接采用 [`personal-marketplace.json`](personal-marketplace.json)；已存在时只合并其中的 `longtask` 条目并保留其他条目。该条目的本地源必须保持为 `./plugins/longtask`，不要为默认个人市场执行 `codex plugin marketplace add`。

```bash
codex plugin add longtask@personal
```

随后启动全新 Codex 任务，确认插件只发现 `$longtask`，旧五个独立入口不再出现。更新或同版本恢复时，先验证新归档并原子替换整个 `~/plugins/longtask`，再执行 `codex plugin remove longtask@personal` 和上述安装命令以清除旧缓存；不得复制零散技能或直接安装可变工作区。

交付包同时包含 `hooks/hooks.json`、平台启动器和只读压缩桥脚本。先按[解释器绑定合同](平台适配器.md#内置压缩信号桥)核验当前主机的 Python 和实际 hook shell，在该插件的宿主数据目录写入绑定；保留已有绑定备份并单独验证，不修改归档内字节或全机 PATH。安装后的全新任务中，通过宿主 `/hooks` 核对插件来源、两个同步事件及实际命令，并按实际字节审阅/信任；版本替换后重新检查信任状态。没有受信或未启用时仍可使用技能，但信号桥不会自动生效。不得默认修改全局 hooks 配置或关闭生产信任校验。适用范围、输入限制和送达证据以[内置信号桥](平台适配器.md#内置压缩信号桥)为准。

### 定位和写入 Python 绑定

`PLUGIN_DATA` 由宿主在**实际插件来源**回调中注入，不是安装终端必然已有的变量。当前实测 Codex 个人市场 `longtask@personal` 的数据目录为 `<Codex 用户目录>/plugins/data/longtask-personal`：默认 Linux 是 `~/.codex/plugins/data/longtask-personal`，原生 Windows 是 `$HOME\.codex\plugins\data\longtask-personal`；自定义 `CODEX_HOME` 时随其变化，与 `plugins/cache/personal/longtask/<version>` 分离。`hooks/list` 的来源路径只定位安装缓存，不提供数据目录，不能由它直接声称已核对 `PLUGIN_DATA`。

目录布局属于宿主实现而非 longtask 的固定协议。核对当前宿主后才能采用上述路径；宿主布局未知时，在隔离任务通过 `/hooks` 核对并信任当前插件的 `PreCompact`，手动 `/compact` 触发实际回调。Windows 缺绑定、或 POSIX 默认解释器调用失败时，启动器错误包含真实 `PLUGIN_DATA/python-path` 位置。该诊断只是安装定位，不证明压缩被阻止；需要禁压缩的任务仍须保留独立禁压缩门。不要把手动设置 `PLUGIN_DATA` 的脚本夹具当作宿主定位证据。

核验解释器的版本与归属后，用已确认的数据目录写入单行绑定。例如，PowerShell 中 `$pythonExe` 和 `$pluginData` 分别是已核验的绝对解释器路径和实际目录：

```powershell
& $pythonExe -E -s -B -c 'import sys; assert sys.version_info >= (3, 14); print(sys.executable)'
if ($LASTEXITCODE -ne 0) { throw 'Python verification failed' }
New-Item -ItemType Directory -Force -Path $pluginData | Out-Null
$binding = Join-Path $pluginData 'python-path'
# 已有绑定先备份到本次安装备份目录；勿覆盖链接或无关配置。
[IO.File]::WriteAllText($binding, $pythonExe + "`n", [Text.UTF8Encoding]::new($false))
```

POSIX 在核验/备份后使用 `printf '%s\n' "$pythonExe" > "$pluginData/python-path"`；不得把路径内容当命令求值。随后在全新任务核对 `source=plugin` 的 `hook/completed` 和实际解释器调用结果；解释器直接调用通过不代替插件链验证。数据目录独立保留，插件升级或缓存重装不会要求把绑定写入归档。

用户另外明确选择禁压缩时，可按[可选同步禁压缩门](平台适配器.md#可选同步禁压缩门)登记随包独立脚本；它不要求替换仍有活动任务的旧插件，安装技能也不会自动启用。上下文配置和门的登记/信任须分别核对，生产策略生效不能用源码测试代替。

## 单宿主发布门

发布证据只覆盖个人 Codex CLI。核心场景、重复采样、适用性与证据要求以[评测协议·黑盒智能体执行评测](评测协议.md#黑盒智能体执行评测)为唯一权威。必须验证当前受信归档的真实行为、授权边界和恢复；个人发布不把未认证的宿主标识冒充高保证身份。

`release_gate` 判断核心发布资格；`benchmark_gate` 判断能否声称成本或性能收益。完整对照缺失只阻止后者，关键行为或恢复缺失仍阻止前者。静态合法的部分完成记录可以保留已通过的宿主层；命令 `--require-release-pass` 列出具体剩余条件。

## GitHub 候选预发布

源码仓库的 `.github/workflows/release.yml` 在推送 `main` 后自动检查 `release-manifest.json` 的版本是否已有公开 Release；也接受匹配版本的标签推送及在 main 上手动重试。正常升级只需同步版本元数据与版本说明并推送主分支，不需要手动创建标签或配置本地 `push.followTags`。

检测由源码侧 `.github/scripts/publish_candidate.py plan` 以只读令牌完成：已有公开版本直接跳过，不因后续同版普通提交重复发布；只有明确的 404 才按资源不存在处理，API 失败不猜测成缺失。只读检测不保证草稿可见；发布任务以写权限分页核对 Release 列表，在任何远端创建前拒绝同版本未完成草稿，核对并删除草稿后可重试。已有未发布标签必须指向本次提交，否则报错，不移动标签或覆盖旧资产。

标签存在性只查询精确 `git/ref/tags/vX.Y.Z`，核对返回的完整 `refs/tags/vX.Y.Z`；不以通用提交查询或前缀匹配代替。轻量标签直接核对提交；附注标签沿 `git/tags/{sha}` 解引用，最多读取八个标签对象并拒绝循环、无效对象及非提交终点。只有最初精确引用的 404 表示标签缺失；已引用对象的 404、422 或其他 API 错误均失败关闭，不据此创建新标签。

需要新候选时，先复用仓库检查，再构建完整 ZIP、核对源码与归档、比较双构建摘要并执行提取后的安装工件自检。只在这些检查通过后，以发布任务的 `contents: write` 创建缺失的 `vX.Y.Z` 标签并在同一工作流中发布公开 GitHub prerelease，上传 ZIP 与 SHA-256 文件；不设为 Latest，不覆盖同标签已有 Release。标签与清单版本、实际检出提交绑定，发布前再次核对标签。全工作流使用同一并发组及 `queue: max`，串行发布并容纳最多 100 个等待运行，避免连续版本推送替换已有等待运行；超出队列容量的运行仍可能被取消。

自动创建标签使用内置 `GITHUB_TOKEN`，不依赖它触发第二个工作流，不要求个人访问令牌。新建标签后的精确引用若暂时返回 404，立即核对一次，再按 1、2、4、8 秒退避核对，最多五次、累计等待 15 秒；每次仍核对提交一致性，其他 API 错误、异常记录或提交漂移立即失败，不重复创建标签。耗尽后停止发布并允许重试工作流。已有匹配标签且缺少 Release 时允许恢复发布；已有公开 Release 时重试仍跳过。上传中断留下的草稿保持可见，不自动删除或替换。

候选预发布只表达源码、确定性合同和工件自检通过，不能代替上述单宿主发布门。真实宿主与恢复证据不随 Git 分发，工作流不生成、不重绑它们，也不自动升级为正式 Release。正式发布仍须在当前受信归档和当前证据上运行 `--require-release-pass`，通过后再取消 prerelease 标记。

工作流必须存在于被推送提交中；首次启用时可在下次 main 推送或手动运行中补发当前尚未发布版本。GitHub Actions 的运行、令牌写权限与仓库规则须允许创建版本标签；本地验证不证明 GitHub 发布 API 已执行成功。源码侧发布边界测试由 `.github/tests/test_publish_candidate.py` 消费 helper，CI 执行；它们不属于安装包的运行时或自检闭包。

版本修改必须提交并到达远端 main 才能触发自动候选；本地版本号改变不会更新 Releases。定位未更新时，按远端清单版本、对应提交的 Candidate release 检测/检查/发布任务与公开 Release 逐项核对，仓库检查通过不等于发布通过。修复发布 helper 后推送包含修复的新提交，或在更新后的 main 手动运行；重跑旧运行仍检出旧提交，不会采用新修复。

各版本用户可见变化统一维护在根[版本说明](../版本说明.md)，以唯一且非空的 `## X.Y.Z` 章节对应清单版本。候选发布从标签提交读取该章节作为 Release 正文，并追加本次源码提交、归档摘要和验证范围；缺失、重复或空章节阻止发布。版本说明随完整归档分发，不包含任务轮次日志或原始运行结果。已发布标签与资产保持不变；说明和工作流更新经新的提交与后续版本发布生效，不移动旧标签补发。

## 当前版本恢复门

不做跨版本回滚。恢复演练必须绑定同一当前归档，并验证：

1. 受信摘要验证通过；
2. 工作区状态和用户项目先完成独立备份；
3. 在空暂存目录完成干净安装；
4. 模拟失败安装后能清理未完成暂存物且不破坏现有安装；
5. 从同一当前版本受信归档完整重装；
6. 全新 Codex 会话能重新发现技能并完成代表性恢复流程。

恢复汇总状态必须由全部机械子检查推导；通过时必须携带当前归档摘要及 run/trace 关联。恢复不是状态降级，也不得把旧状态写入当前 schema。

## 兼容性策略

- 项目检查点按[当前版本边界](状态协议.md#当前版本边界)支持同一大版本的次版本和补丁兼容恢复；跨大版本拒绝，结构与证据校验保持有效，不需要清理或重建有效旧任务。
- 不提供跨大版本迁移、检查点版本改写或自动插件回滚。跨大版本历史工作区可在隔离副本中用对应历史工具只读取证，不能继承为当前任务的批准或完成。
- 新任务初始化当前完整技能版本；兼容续接保持原任务及创建版本。插件故障重装与当前归档发布验证仍绑定准确受信工件，内容修复按版本推进生成新版本。

最终发布检查：

```bash
python3 scripts/validate_longtask.py --require-release-pass
```

## 已安装工件自检

在从受信归档提取的插件根执行 `python3 scripts/validate_longtask.py --installed`。该模式验证嵌入逐文件清单、安装闭包和随包合同，不要求未随包分发的宿主、调用和前向运行结果；它与 `--require-release-pass` 互斥，不能证明上线通过。默认源码校验不要求运行结果，也不验证宿主发布资格；`--with-evaluation-results` 显式核验本地调用、前向、记忆与宿主证据，缺失或过期即失败。正式发布门 `--require-release-pass` 仍要求这些当前结果、候选归档和通过的宿主/恢复门，不因结果移出 Git 而降级。单元测试使用独立的合成 fixture，提取后也可运行。
