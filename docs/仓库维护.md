# 仓库维护

本文定义 longtask 仓库的内容职责和维护约定，供使用者与贡献者阅读；它不是普通项目执行 longtask 时默认加载的工作流。规范依据于 2026-10-09 核对。

## 内容职责

| 内容 | 唯一职责 | 维护原则 |
|---|---|---|
| `README.md` | GitHub 首页与使用导航 | 先说明用途、要求与上手路径，再链接完整合同；声明必须与实际证据一致 |
| `.github/CONTRIBUTING.md` | 贡献入口与本地验证步骤 | 引用仓库维护规则，不复制状态或审查合同 |
| `.github/SECURITY.md` | 安全问题报告入口 | 区分漏洞与普通问题，提供可用的私下渠道，不承诺未经确认的服务时限 |
| `.github/CODE_OF_CONDUCT.md` | 社区参与及处理原则 | 清晰、简短，适配个人维护项目 |
| `.github/ISSUE_TEMPLATE/` 与 PR 模板 | 结构化反馈 | 收集版本、复现、预期行为与证据；避免要求未创建的标签或不存在的服务 |
| `.github/workflows/` | 自动仓库检查与标签候选发布 | 最小权限、固定 Action 提交、有界运行；检查名称准确表达保证范围 |
| 根及 `skills/*/SKILL.md` | 技能发现与执行指令 | 按模式渐进加载；共享规则的权威来源见 [AGENTS.md](../AGENTS.md) |
| `skills/*/agents/openai.yaml` | Codex 展示与调用策略 | 展示与实际入口一致；默认提示明确使用对应技能 |
| `docs/ARCHITECTURE.md` 与模块文档 | 当前项目知识 | 按[文档架构](../文档架构.md)维护；不保存已完成任务过程 |
| `release-manifest.json` | 可安装工件的完整闭包 | 发布合同见[发布与恢复](../references/发布与恢复.md) |

GitHub 识别的社区文件使用固定英文名称；其他人读文档按职责命名为中文。命名权威见[文件命名](../文档架构.md#文件命名)。新增内容必须有实际读者、入口与维护职责，避免为填满模板创建无人使用的文档。

## 说明文档分工

README 面向使用者：说明适用场景、安装、入口选择和验证边界。根 `SKILL.md` 面向执行者：维护路由、共享不变量和完成边界；子技能只说明各模式的决策与出口。界面短说明使用用户能直接理解的动作和结果，触发条件仍由 frontmatter 定义。

协议与操作示例保留精确字段、失败语义和条件细节；入口只给消费时机与链接，不复制工具清单或要求全量预读。精简正文时保留必要安全约束与稳定引用，避免通过省略改变合同。

## Skill 格式与项目约定

[Agent Skills 规范](https://agentskills.io/specification)要求 `SKILL.md` 包含 `name`、`description`。名称须与技能目录一致，采用小写字母、数字与单连字符，最长 64 字符；描述非空、最长 1024 字符，说明能力及触发场景。`license`、`compatibility`、`metadata` 等是可选字段，`metadata` 值为字符串。

longtask 的项目约定是：所有入口声明 `license: MIT`、Codex 与 Python 3.14+ 环境要求、字符串形式的 `metadata.version`。根 `SKILL.md` 是共享合同，`skills/longtask/SKILL.md` 是插件发现入口；两者不是两个可独立安装的插件。六个入口各有 `agents/openai.yaml`，使用带引号的字符串和 `policy.allow_implicit_invocation: true`。这些是本项目的维护约定，不是通用规范的必填项。

[Codex 官方 Skill 文档](https://developers.openai.com/codex/skills)定义可选 UI 元数据与隐式调用策略，并推荐通过插件分发可复用的技能。`default_prompt` 使用相应的 `$skill-name`；不把 UI 字段当作执行授权，不用实验性的 `allowed-tools` 字段扩大宿主权限。插件资源共享及安装方式遵循本项目的发布合同。

技能说明只保留会改变决策的指导。共享不变量只维护一次，条件细节放入可发现的参考，不为每种情形引入固定流程；根文件保持在 500 行以内。描述按真实触发边界精简，模式参考注明消费者与加载条件。名称或描述变化需要更新路由案例并重新评测。

精简同时核对发现面、根文件与实际模式读取路径，避免把正文搬到默认必读的参考而增加总负担。文本体积、确定性合同和真实宿主效果分别度量，方法见[评测协议](../references/评测协议.md)；模型名称不参与状态机分支或替代完成证据。

## 自动检查与证据

CI 在 Pull Request、`main` 推送、手动触发及标签候选发布调用时运行单一 Python 3.14 检查任务，不使用版本矩阵。工作流 Action 固定到完整提交 SHA，Dependabot 定期提出更新；检查任务令牌只授予读取仓库的权限，候选发布任务单独授予 `contents: write`，发布令牌只在上传步骤传入环境。检出不保存凭据，不使用 `pull_request_target` 执行贡献代码。运行时脚本不需要安装第三方 Python 依赖。

CI 检查调用语料与前向案例映射，再执行单元测试和当前前向套件，最后验证源码候选；新克隆不需要本地运行结果。检查不自动重绑调用结果或伪造宿主样本，也不执行正式发布；通过不证明已安装宿主行为与性能收益。标签候选发布的触发、工件与证据边界统一见[GitHub 候选预发布](../references/发布与恢复.md#github-候选预发布)。各证据层的定义以[评测协议](../references/评测协议.md)为准。

本地命令、评测更新及 PR 验收入口见[贡献指南](https://github.com/J-ChenX/longtask/blob/main/.github/CONTRIBUTING.md)。脚本校验前置字段、引用和闭包；行为改变必须由相应运行证据验证，不能仅用模板完整性证明。

## 发布材料与仓库材料

`docs/` 的当前架构、模块和维护文档进入发布闭包，使归档内 README 导航可解析。GitHub 社区文件、工作流及 Dependabot 配置仅服务源码仓库，不进入安装工件；归档内需要它们时链接到 GitHub。仓库与产物的归属规则统一见 [AGENTS.md](../AGENTS.md#源码与产物架构规范)；证据格式及发布资格仍由评测与发布合同定义。

修改随包文件会改变候选摘要。旧宿主样本不得重绑到新归档；尚未实测的候选维持 `unable_to_verify` 与阻塞的发布门。正式发布必须另外完成[单宿主发布与恢复验收](../references/发布与恢复.md#单宿主发布门)。GitHub Release、版本号和支持声明只能表达已经验证的状态。
